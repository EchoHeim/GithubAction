## CI 第二轮：WAF 时序竞态 + 同日重复回执漏词（11:00–11:15）

### 好消息：机房 IP 认这份 Cookie

CI 日志里 `Cookie 注入: 成功 23 项` → **`Cookie 登录态有效`** —— 说明 Discuz 的 auth
不绑 IP，机房 IP 也能复用这份登录态。剩下要过的只有 WAF。

### Bug 1（CI 必现，本机不复现）：`pass_waf()` 读到「上一页」误判通过

```
RuntimeError: 签到任务：页面不是登录态：url=https://www.52pojie.cn/waf_text_verify.html
```

原因：`get_web_driver()` 设了 `page_load_strategy="none"`，`driver.get()` 立刻返回，
而 `pass_waf()` 只固定 `sleep(1.5)` 就判断——那时 DOM 还是**首页**（没有 WAF 标记），
于是 `is_waf_page()` 返回 False → 误判「已通过」。等真正去用页面时，WAF 页已提交。
本机延迟小没暴露，CI 上必现。

修法：用 **`performance.timeOrigin`** 判断「新文档是否提交」——每次导航都会变，
与 URL、页面内容都无关，比 sleep 和 current_url 都可靠：

```python
origin = _document_time_origin(driver)   # 导航前
driver.get(url)
wait_new_document(driver, origin)        # 等 timeOrigin 变化 = 新文档已提交
wait_document_ready(driver)              # 等 document.readyState != 'loading'
time.sleep(1.0)                          # 再给 WAF 的 JS 落地留点时间
```

另外 `open_task()` 改成**循环确认**（`WAF_ATTEMPTS`，默认 3）：过完验证码后站点有可能
再挑战一次，所以「pass_waf 返回 True」不等于「现在就在目标页」；确认前先等 DOM 就绪。

### Bug 2（本机第二次跑就撞到）：同日重复跑的回执匹配不上

```
===> 签到任务 回执: 抱歉，本期您已申请过此任务，请下期再来
RuntimeError: 签到任务回执无法识别            ← 关键词里只有「已经申请过」，漏了「已申请过」
```

修法：`TASK_ALREADY_MARKERS` 补「**已申请过**」「请下期再来」。
影响面：定时任务 + 手动触发同一天跑两次时，第二次会误报失败 —— 必须修。

单测 5 种回执分类：`already / success / not_login / success / unknown` 全部正确。

### 本机回归（11:10）

### 关键定位（都是本机只读探测 + CDP 抓包得出的）

- **积分**：页头 `a#extcreditmenu` → 文本「积分: 56」。读它即可，不用进积分页。

  那边页面上明写「本区禁止无关回复」，差点选错板块。**别按 cookie 猜 fid，要查列表页。**

  帖子链接形如 `thread-<tid>-1-1.html`，标题在 `a.s xst` 里。
- 帖子页快捷回复：`form#fastpostform` + `textarea#fastpostmessage` + `button#fastpostsubmit`，
  当前不要求验证码（`seccodeverify` 计数 0）。发表回复按钮旁边有版规提示：
  「禁止复制他人回复等『恶意灌水』行为，违者重罚」。

### 踩的两个坑（都是「判定」问题，不是提交问题）

1. **`#fastpostreturn` 里有隐藏的 `#fastpostreturn_wait`**（内容恒为「请稍候...」），
   而 `textContent` **连隐藏文本一起读** → 每次都读到「请稍候...」→ 永远等不到结果。
   之前 v2ex 那边的经验是「用 textContent 读隐藏元素」，这次反过来被它坑了：
   **同一个 API，读隐藏元素是优点，遇到「隐藏占位符」就是陷阱**。要么排除占位符，
   要么换判定源。
2. **Discuz 的回帖响应是注入 `<head>` 的 `<script>`**：
   `succeedhandle_fastpost('forum.php?mod=viewthread&tid=…&pid=55941092&page=14…', '非常感谢，回复发布成功…')`。
   这套主题里**没有定义 succeedhandle_fastpost**，所以成功也不跳转、界面无变化。
   判定必须扫脚本文本 —— 用 CDP 的 `Network.getResponseBody` 抓到响应体才看明白。

### 教训：前三次「超时失败」其实都成功发出了回复

脚本判定错 → 报失败 → 每次重跑又真发一条 → **今天一共发了 4 条**（2129303 / 2126637 /
2125118 / 2129983），末页都能查到「谢谢分享~」。**判定不确定时不要自动重试副作用操作**，
这条要记牢。

### 缺口识别（踩了两坑才定）

1. **元素截图不能用来匹配**：Selenium 的元素截图是**合成后的画面**，会把拼图块本身也拍进去
   → 匹配退化成「匹配到自己」，`left=0 / 置信度 1.0`。
2. **拼图块是「亮版」，背景缺口是压暗的** → 直接像素匹配落到云/岩石上（0.80）。
   改用原始图片 + **带 alpha 掩码的 `TM_CCOEFF_NORMED`**（对线性明暗变化不敏感）+
   掩码腐蚀掉自带白描边 → 0.95~0.99，二维落点正落在缺口上。
3. 原始→渲染换算 = `渲染宽 / naturalWidth`（340/552 = 0.6159），与旧脚本的 `left*340/552` 一致。

### 拖动：能拖，但过不了服务端

- 位置精确：拼图块位移与计算距离**逐像素吻合**（例：算 221px → x=20 → x=241）。
- 事件送达 OK：iframe 内 `pointerdown/move/up` 都收得到。
- 早期被 `{"code":502,"message":"操作过快，请慢一点[5014]"}` 拒 → 用 CDP
  `Input.dispatchMouseEvent` + 显式时间戳做平滑轨迹（点间隔 16~50ms、时长 1.2~1.5s）。
- **坐标坑（重要）**：Selenium 在 iframe 内给的是 **iframe 局部坐标**，CDP 要**顶层视口坐标**
  → 必须加 iframe 的 rect 偏移，否则按下点打空、拼图块纹丝不动。
- 平滑轨迹之后服务端变成**静默拒绝**（无错误文案、拿不到 `sessionid`）。
  结论：字节 verifycenter 是 **ML 行为风控**，合成事件难以稳定通过；继续调参性价比低。
