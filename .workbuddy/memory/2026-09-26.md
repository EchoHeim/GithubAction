## 追加：TimeoutException 真因 = 英文界面，选择器全部押在中文文案上

**CI 第二轮日志**（目录问题已修好，暴露下一层）：
`===> 第 N 次登录异常: TimeoutException('', None, [...])`，url 停在 `edge.v2ex.com/signin`。

**真因（本地可复现，非猜测）**：V2EX 按 `Accept-Language` 切界面文案。
CI 是海外 IP → **英文界面**（标题 `V2EX › Sign In`），本地中文 → 标题 `V2EX › 登录`。
实测两种界面下的选择器命中：

|---|---|---|
| `//*[@placeholder='请输入上图中的验证码，点击可以更换图片']` | 1 | **0** |

## 环境坑（重要，避免重复踩）

**本机 shell 里有 `http_proxy=http://127.0.0.1:8120` 等代理变量。**
Selenium 的 urllib3 会把它套到发往 **localhost:chromedriver** 的请求上，代理回一句
`WebDriverException: Message: unhandled request` —— 现象是"能建会话但任何命令都失败"，
极易误判成 chromedriver/Chrome 版本不匹配（09-24 就被这个假象带偏过）。
跑本地 selenium 必须先：
`unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY all_proxy ALL_PROXY && export NO_PROXY=localhost,127.0.0.1 no_proxy=localhost,127.0.0.1`
另外：沙箱内起不了 Chrome 会话，需要沙箱外执行。

## 追加 3：登录成功了但没领到奖 —— session 不跨域 + 盲点按钮假报成功

用户反馈：CI 日志显示「v2ex 登录成功」「已点击今日奖励」，但实际没领到。

### 真因 1：V2EX 的 session cookie 是 host-only，不跨域

实测（`%TEMP%\wb_v2ex_cookie_check.py`）：

| 访问 | PB3_SESSION 的 domain |
|---|---|
| `https://v2ex.com/` | `v2ex.com` |
| `https://edge.v2ex.com/` | `edge.v2ex.com` |

两个域**各签各的**，都不是 `.v2ex.com`。所以之前 `V2EX_SIGNIN_URL=edge.v2ex.com`
登录后去 `v2ex.com/mission/daily` 必然被踢回 `v2ex.com/signin?next=/mission/daily`（实测如此）。

**修法**：`V2EX_SIGNIN_URL` 默认改成 `https://v2ex.com/signin`，整套流程同域。
实测两站登录页结构**完全一致**（搜索框→用户名→密码→验证码→提交、`img#captcha-image`、
中英文 placeholder 都一样），选择器无需改。老站 form action = `https://v2ex.com/signin`。

### 真因 2：宽选择器在错误页面上盲点，且无任何校验就打印成功

- `//*[@type='button']` 在「被踢回的登录页」上唯一能匹配的是页脚 `<button class="scroll-top">`
  （实测 `element_to_be_clickable` 因它是隐藏态而超时）。
- CI 那次能「点成功」，是因为 `get_web_driver()` 设了 **`page_load_strategy="none"`**，
  `driver.get()` 立即返回、DOM 可能还是上一个页面 —— 查到并点了上一个页面的残留元素。
- 全程没有校验，`print("已点击...")` 就算成功。

**修法**：base.py 新增 `wait_url(driver, needle, timeout)` / `wait_visible(driver, xpaths, timeout, label)`；
`claim_daily` 重写：每步先等 URL 落地再查元素 → 回首页确认登录态（无 `/signout` 即失败）→
点首页领奖入口 `//a[contains(@href,'/mission/daily')]`（href 匹配，语言无关）→
确认落在任务页 → 点 `input[type='button']`（只认 input，避开页脚 `<button>` 和 `type=submit`）→
处理可能的 confirm → 校验领取按钮是否消失。任何异常 dump 现场 + 抛错。

### 补充：区分「今日已领取」与真失败

首页领奖入口只在「今天还没领」时存在，领完即消失 → 拿它当领取状态判据。
已确认登录态却没有入口 → 判定今日已领取、正常结束（仍留 `claim_entry_absent` 现场备查）。
否则同一天重复跑会因任务页没按钮而误报红。

**交付**：`21e7d2f`（同域 + 领奖流程重做）、`4f664d0`（已领取判定）。

**验证**：老站中英文结构各 3 项全 PASS；`wait_url` 错误 needle 不误判；
负面测试（未登录）抛 RuntimeError + 留现场，不再假报成功；离线单测 18 项全过。

**教训**：`page_load_strategy="none"` 下，`driver.get()` 之后的每一次元素查询都必须

## 追加 4：领奖**成功**了却被判失败 —— 成功判据想当然（CI 实跑反馈）

用户贴 CI 日志：`notice: 已成功领取每日登录奖励 4 铜币`，但仍然

**真因**：我以为「领取成功后领取按钮会消失」，实际 V2EX 只是把
`<input type="button">` 的 value 从 `领取 X 铜币` **改成 `查看我的账户余额`** ——
按钮还在、只是文案变了。旧判据 `wait_visible(("//input[@type='button']",))` 一查还在就当成失败。

（顺带发现：CI 日志里按钮 value 字面就是 `领取 X 铜币`，X 没被替换成数字，但语义判断不受影响。）

**修法**（`ced17ee`）：
- 新增 `is_claim_value(value)`：按文案语义判断是否仍「可领取」（含「领取」/ `claim` / `laim`）
- 新增 `_visible_claim_buttons(driver)`：只挑「可见 + 仍可领取」的 `input[type=button]`
- 新增 `find_claim_button(driver, timeout)`：等出现可领取按钮；顺带解决「页脚 `<button>` 误命中」
- 删掉 `CLAIM_BUTTON_XPATHS`（带 `//input[@type='button']` 宽兜底的那组）
- 成功判据三选一：**页面出现「已成功领取」提示 / 已无可领取按钮 / 按钮文案不再表达可领取**
- 只有「仍存在可领取按钮」才 dump `claim_button_remained` + 抛错

**教训（通用）**：**别拿「元素消失」当操作成功的判据。** 很多站点成功后不改 DOM 结构、只改文案/属性，

## 追加 5：聚宽（JoinQuant）签到失败 = 出口 IP 地区限制，非代码问题

用户问「聚宽登录失败为什么」。**结论：不是选择器/账号/密码的问题，是 GitHub runner 的海外出口 IP 被聚宽地区封禁。**

**证据（本地实测对照）**：同一个 `POST https://www.joinquant.com/user/login/doLoginByText`
（假凭据）——本地（东莞，大陆出口）返回 **200 + JSON** `{"code":"20000","msg":"用户不存在或密码错误"}`，
说明接口本身是活的、报的是业务错误；CI 上是 **405 + text/html + non-json**，
说明请求**根本没到应用层**，被边缘层（CDN/WAF）拦了。

注意：聚宽正常响应也是 `content-type: text/html` 但 body 是 JSON，所以**判据要看 body 而不是 content-type**。

**连锁反应**：网页入口先被替换成「当前地区暂不支持访问」页 → 后面 7 个 `try`
（登录/积分/签到/社区/文章/回首页/领积分）全部 `find_element` 找不到元素 → 刷一屏假失败。
真正失败的只有第一步。

**历史**：`JoinQuant.py` 自 fork 初始提交（`38a3e5d`）就在，`339a177`（09-08）才加上 API probe 调试。
即聚宽签到**在 Actions 上很可能从来没成功过**，不是最近坏的。

**可行解法**：① 搬到国内机器（腾讯云轻量）+ cron，脚本原样可用；② Actions 里挂大陆出口代理
（前提是有大陆代理，且要同时给 requests 的 env 和 Chrome 的 `--proxy-server`）；
③ 接受现实，摘掉 workflow 里的聚宽步骤或加早退，别再每天推失败卡片。

**待办**：脚本目前地区受限仍会把整套流程跑完并推飞书失败卡片，建议检测到「当前地区暂不支持访问」
后 early return，避免刷一屏假失败。另 `sys.path.append("current_folder/../")` 漏了 `f` 前缀
（字面量不是变量），只因 workflow 用 `python -m` 从仓库根运行才被掩盖。

## 追加 7：探接口的结论 —— 聚宽有自研拼图滑块，纯 API 方案不划算

lodge 问「能不能挂 GitHub / Gitee 远程自动跑」，我选了先探接口那条路（他拍板）。结论推翻了原先的判断：

**1. 纯 requests 抄接口行不通，因为登录/签到都过风控滑块**
- `jacek4yang/astock-terminal`（Rust）注释写明：`doLoginByText` 成功返回**字符串** `code="00000"`，
  **触发风控返回数字 `105`**，此时要先解题拿 `valideCode` 再重放登录。
- `lzwme/ql-scripts` 的 `ql_joinquant_checkin.py`（青龙脚本）开头即写：
  「验证码策略：拦截 captchar API 获取 bgImg/hqImg，OpenCV 识别缺口位置，自动拖动滑块」。

## 追加 9：FishPi 禁用 + V2EX 补飞书推送

### 先纠正一个我自己的误判

追加 8 里我说「45 分钟是被 JoinQuant 撑起来的，现在偏冗余」——**错了，是被 FishPi 撑的**。
`fishpi.py:111-140` 有 6 次聊天发言，每次后面跟 `time.sleep(300)`，共 30 分钟，
同一个 try 里顺序执行。所以 lodge 后来说「收到 20」时我先拦了一下并说明原因。
他随后要求**把 FishPi 也禁用** —— 禁掉之后 20 分钟立刻合理了。

### check_in.yml

- FishPi 步骤改 `if: false`（**保留 env 和 run 不删**，恢复只需把条件改回去，原条件写在注释里）
- `site` 选项收敛为 `all` / `v2ex`
- job `timeout-minutes` 45 → 20
- V2EX 步骤补上 `FEISHU_BOT_ID` env 与第三个命令行参数

### v2ex.py

- `read_balance(driver)`：**只认 href 里的 `/balance`**（V2EX 按 Accept-Language 切语言，
  文案会变、链接不会），返回 `(展示文本, outerHTML)`，HTML 打进日志便于以后修解析
- `claim_amount(value)`：从「领取 4 铜币」/「Claim 12 coins」里抠数额，抠不到返回空串
- `notify(bot_id, status, balance, claimed, note)`：飞书卡片四行；**推送失败只 WARN，不判签到失败**
- `claim_daily` 返回值从裸 `return` 改成 `(状态, 本次领取数额)` 二元组
- `v2ex(username, password, bot_id="")`，`argv[3]` 可选，不给就不推

**踩坑点（重要）**：`finally` 里读余额必须 `except Exception`，**不能只 catch `WebDriverException`**——
在 finally 抛出的异常会顶掉原始异常，把真正的失败原因盖掉。

**验证**：`py_compile` 通过；离线单测 **28/28**（`%TEMP%\wb_v2ex_feishu_test.py`，mock 掉飞书与 driver）。

notify 三种内容形态 + 推送异常吞掉、无裸 return、三个函数签名、返回值解包。
